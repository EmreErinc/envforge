[CRITICAL] Test Environment Contamination in Encryption Suite
─────────────────────────────────────────────────────────────────────────────
Evidence:
  - Test: `test_env_age_key_empty_is_rejected` (tests/encryption_invariant_tests.rs:194)
  - Failure: Fails with parallel execution; passes with --test-threads=1
  - Root Cause: Test `test_env_age_key_invalid_key_fails_encrypt` (line 206) sets 
    ENVFORGE_AGE_KEY to invalid key; prior test fails to properly isolate env state
  - Failure Output: 
    "empty ENVFORGE_AGE_KEY must be rejected, got: Ok(Zeroizing(
    'this-is-not-a-valid-age-key'))"

Impact:
  - Encryption rejection logic bypassed under parallel test execution
  - CI passing but real-world deployment may inherit parent process env vars
  - Age key validation inconsistent between single/multi-threaded contexts

Recommendation:
  - Guard all env var tests with per-test mutex: static ONCE: std::sync::OnceLock<()>
  - Use guard pattern: let _guard = LOCK.get_or_init(|| Mutex::new(())).lock()
  - Alternatively: Save/restore full env state before each test
  - Add #[serial] attribute from serial_test crate if available
  - Priority: MUST fix before next release

Status: FAIL — Acceptable if tests run with --test-threads=1 (current CI does not enforce this)

────────────────────────────────────────────────────────────────────────────────

[CRITICAL] LSP Plugins Unsigned — Supply Chain Risk
─────────────────────────────────────────────────────
Evidence:
  - VSCode Extension: editors/vscode/package.json — publisher: emreerinc (unverified)
  - IntelliJ Plugin: editors/intellij/ — no code signing verification
  - No GitHub release artifacts signed (no .asc, no cosign)
  - Marketplace verification: VSCode publisher account unlinked to organization

Impact:
  - Anyone with access to npm/marketplace could push malicious plugin version
  - LSP extensions run in editor process (IntelliJ) or isolated (VSCode) — full
    access to workspace files if injected
  - No attestation of binary correctness or source provenance
  - Users unable to verify they're running official plugin

Recommendation:
  - Sign VSCode extension with Microsoft Identity certificate
  - Sign IntelliJ plugin with Jetbrains marketplace signing infrastructure
  - Publish SHA-256 checksums of binaries in GitHub Releases signed with GPG
  - Consider Sigstore/cosign for zero-friction verification
  - Add CI workflow: GitHub Actions to sign on release tag
  - Document verification: README.md → How to verify plugin authenticity

Status: CONCERNS — Medium severity for IDE plugins (limited damage vs. CLI binary)

[HIGH] Audit Trail Gaps for LSP Secret Access
──────────────────────────────────────────────
Evidence:
  - File: src/lsp/server.rs — Line 230: "audit log records which LSP endpoint 
    triggered the mutation"
  - Reality: LSP protocol is stateless HTTP-like; hover/completion requests 
    are NOT logged
  - Audit log: ops/monitor/mod.rs — emits KeyProvisioning, FileChange events 
    only
  - Gap: If IDE plugin exposes secret value in error message/hover/completion, 
    no audit record

Impact:
  - Unaudited secret exposure via IDE plugins (VS Code redaction tests exist 
    but hover logging missing)
  - No user accountability if secrets leaked via IDE workflow
  - Cannot correlate secret exposure with editor actions

Evidence of Testing:
  - tests/lsp_security_tests.rs — redaction tests exist
  - tests/lsp_redact_tests.rs — confirms sanitize_value() removes secrets
  - BUT: No audit trail assertions for LSP operations

Recommendation:
  - Log ALL LSP operations that touch sensitive variables to audit trail
  - Include: method, variable name, user (if available), result
  - Add test: test_lsp_hover_on_secret_emits_audit_entry
  - Consider: rate limiting audit log writes to prevent DoS by repeated hover

Status: CONCERNS — Medium (redaction in place, logging incomplete)

3. DATA PROTECTION

  - Key storage: ~/.config/envforge/age.key (0600 permissions)
  - Format: ENC[age:base64...] embedded in shell files
  - Cache: credentials.toml + secrets-cache/* (encrypted, 0600 perms)

Evidence:
  - src/ops/encrypt.rs — age key resolution with env var priority
  - Line 59-62: Rejects empty ENVFORGE_AGE_KEY

  - test_env_age_key_empty_is_rejected: PASSES (with --test-threads=1)

    encryption

In Transit:

  - Cert pinning: x509-cert parsing + certificate validation (ADR-015)
  - Provider credentials: Passed via env vars or stdin (never CLI flags)

Evidence:
  - src/cli/secrets_cmd.rs — "Secrets on argv are visible in /proc/PID/cmdline"
  - Credential isolation enforced in all 13 providers

Key Management:
  - Primary key: Auto-generated on first run, stored in config dir
  - Recovery key: age-recovery.key (0600) — generated alongside primary
  - No key rotation: Manual replacement required (documented in SECURITY.md)
  - Env override: ENVFORGE_AGE_KEY (highest priority) + ENVFORGE_AGE_KEY_FILE

Tests:

Memory Protection:
  - Zeroize on drop: src/ops/encrypt.rs returns Zeroizing<String>
  - Volatile mode default: VolatileMode::On (secrets auto-expire)
  - ARGV detection: Can disable with ENVFORGE_UNSAFE_ARGV in debug builds only

Evidence:
  - src/ops/secrets/modes.rs — VolatileMode enum with TTL support
  - zeroize crate in Cargo.toml (v1)
  - tests/security_memory_tests.rs (233 tests on memory safety)

Shell Injection Resistance:

  - Injection scope: Limited to export/env var parsing (not command execution)
  
Evidence:

  - Shell syntax support: Detects bash/zsh/fish/sh differences but doesn't 
    execute
  - Escape sequence handling: Line 297 — "In double quotes, backslash escapes 
    next char"
  - Test: tests/parser_tests.rs (300+ test cases)

Error Message Sanitization:
  - Function: src/ui/sanitize.rs — strip_ansi_escapes(), strip_control_chars()
  - Coverage: Removes ANSI CSI sequences (e.g., \x1b[31m) and control chars
  - Tests:
    - test_strip_ansi_csi() ✓
    - test_strip_ansi_complex() ✓
    - test_strip_control_chars_removes_bell() ✓
  - Secret masking: Error output filtered before display

CLI Argument Validation:
  - Framework: clap (v4) with derive macros (type-safe)
  - Parser enforcement: Numbers validated as u32/u64, not strings
  - Schema validation: .env.schema enforced at deserialize time

Input Bounds:
  - File size: 10MB max (src/parser/parse.rs line 45)
  - Variable name length: No explicit cap (reasonable for env var names)
  - Value length: No explicit cap (limited by shell file size)

Tests:
  - tests/parser_tests.rs — 300+ test cases covering edge cases
  - tests/cli_error_handling_tests.rs — argument validation
  - tests/validation_tests.rs — schema-based validation

Status: PASS — Parser is well-isolated and sanitization is comprehensive

CONCLUSION
═════════════════════════════════════════════════════════════════════════════════

EnvForge v0.8.0 demonstrates STRONG security fundamentals with one CRITICAL
test isolation issue that masks a real encryption validation vulnerability
under parallel execution. 

For production release:
- MUST: Fix encryption test isolation (blocks parallel CI)
- MUST: Sign LSP plugins (supply chain integrity)
- SHOULD: Complete LSP audit logging (operational security)
- SHOULD: Generate SBOM + attestations (compliance & provenance)

Current passing CI is likely due to sequential test execution or env var caching.
The tool's encryption, secret isolation, and input validation are well-designed
and thoroughly tested. The primary gaps are in operational visibility (LSP audit
logging) and artifact provenance (plugin signatures).

Estimated remediation time: 12-15 hours for all recommendations.
